# Mini NPU Simulator

AI 칩(NPU)의 핵심 연산인 **MAC(Multiply-Accumulate)** 를 Python으로 직접 구현해서,
입력 패턴이 십자가(Cross)인지 X인지 판정하는 콘솔 프로그램입니다.

---

## 1. 실행 방법

```bash
python3 main.py
```

- `main.py`와 `data.json`을 **같은 폴더**에 두고 실행합니다.
- Python 3.8 이상, 외부 라이브러리 없음 (표준 라이브러리 `json`, `time`만 사용)

실행하면 모드를 고릅니다.

| 선택 | 모드 | 하는 일 |
|---|---|---|
| 1 | 사용자 입력 (3×3) | 필터 A, B와 패턴을 콘솔로 입력 → 점수, 연산 시간, 판정(A/B/판정 불가) 출력 |
| 2 | data.json 분석 | 필터·패턴 로드 → 케이스별 판정과 PASS/FAIL → 성능 분석 표 → 결과 요약 |

모드 1 입력 예시 (한 줄에 숫자 3개, 공백 구분)
```
필터 A: 0 1 0 / 1 1 1 / 0 1 0   (십자가)
필터 B: 1 0 1 / 0 1 0 / 1 0 1   (X)
패턴  : 1 0 1 / 0 1 0 / 1 0 1   → A 점수 1.0, B 점수 5.0, 판정 B
```

## 2. 구현 요약

### MAC 연산
- 패턴과 필터를 겹쳐서 **같은 위치끼리 곱하고, 그 결과를 모두 더합니다.**
- NumPy 없이 이중 `for`문으로 직접 구현했습니다 (`mac()` 함수).
- 점수가 더 큰 필터 쪽으로 판정합니다.

### 라벨 정규화
data.json은 같은 뜻을 서로 다르게 표기합니다.

| 위치 | 원래 표기 | 표준 라벨 |
|---|---|---|
| expected 값 | `+` | Cross |
| expected 값 | `x` | X |
| 필터 키 | `cross` | Cross |
| 필터 키 | `x` | X |

판정 결과(`Cross`)와 정답(`+`)을 그대로 비교하면 맞혀도 FAIL이 됩니다.
그래서 프로그램 안에서는 모든 라벨을 **Cross / X** 두 가지로 통일한 뒤 비교합니다 (`normalize_label()`).

### 동점 처리 정책 (epsilon)
- `abs(점수A - 점수B) < 1e-9` 이면 **동점(UNDECIDED)** 으로 봅니다.
- 컴퓨터는 0.1 같은 소수를 정확히 저장하지 못해서, 수학적으로 같은 값이 `0.9`와 `0.8999999999999999`처럼 미세하게 달라질 수 있기 때문입니다.

### 오류 처리
- 모드 1: 한 줄의 숫자 개수가 3개가 아니거나 숫자가 아닌 값이 있으면 안내 문구를 출력하고 다시 입력받습니다.
- 모드 2: 키 형식 오류, 필터 없음, 패턴 크기 불일치, 알 수 없는 라벨이 있으면 **그 케이스만 FAIL** 처리하고 사유를 남깁니다. 프로그램은 멈추지 않습니다.

## 3. 결과 리포트

### 3-1. 테스트 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | **FAIL** |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | **FAIL** |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | **FAIL** |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**총 6개 / 통과 3개 / 실패 3개**

### 3-2. FAIL 원인 분석

실패 3건은 모두 **두 필터 점수가 사실상 같아서** 동점(UNDECIDED)으로 판정된 경우입니다.
원인을 "데이터/스키마 문제 vs 로직 문제 vs 수치 비교 문제"로 나누어 진단했습니다.

**① 데이터 문제 (근본 원인): 필터 가중치가 두 점수를 똑같이 만들도록 설계되어 있음**
- size_5_1 (X 패턴): Cross 필터는 가운데 칸만 0.9 → 점수 0.9.
  X 필터는 X 모양 9칸이 각각 0.1 → 0.1 × 9 = 0.9. 두 점수가 같습니다.
- size_13_2 (십자가 패턴): Cross 필터는 25칸 × 0.3 = 7.5.
  X 필터는 가운데 칸 하나가 7.5 → 점수 7.5. 역시 같습니다.
- size_25_1 (X 패턴): Cross 필터 가운데 칸 4.9 → 점수 4.9.
  X 필터 49칸 × 0.1 = 4.9. 같습니다.

**② 수치 비교 문제: 부동소수점 오차가 "가짜 차이"를 만듦**
- 수학적으로는 같은 값인데, 0.1을 여러 번 더하는 과정에서 오차가 쌓여
  `0.9` vs `0.8999999999999999`처럼 맨 끝자리가 달라집니다.
- epsilon 없이 `>`로만 비교했다면 이 오차 때문에
  size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross 로 판정되어 **세 건 모두 정답과 반대**가 됩니다.
  즉, 오차가 우연히 어느 쪽으로 쏠렸느냐에 따라 결과가 정해지는 셈입니다.
- epsilon 정책은 이런 의미 없는 차이를 "판정 불가"로 정직하게 보고하게 해 줍니다.

**③ 로직 문제: 없음**
- 같은 MAC 함수로 나머지 3건은 정상 PASS했고, 모드 1의 3×3 예시도 손으로 계산한 값(5.0, 1.0)과 일치합니다.
- 라벨 정규화를 적용했기 때문에 `+`/`x` 표기 차이로 인한 FAIL도 없습니다.

**개선 방향**
- 코드가 아니라 **필터 데이터**를 고쳐야 합니다. 예를 들어 필터 가중치를 모두 1.0으로 맞추면
  각 패턴이 자기 모양 필터에서 확실히 높은 점수를 받습니다.
- 출제 데이터는 그대로 두고, 이 결과를 "epsilon 정책이 위험한 판정을 걸러낸 사례"로 보고합니다.

### 3-3. 시간 복잡도 분석

**성능 측정 결과** (MAC 연산 10회 반복 평균, 측정 환경에 따라 값은 달라짐)

| 크기 (N×N) | 평균 시간 (ms) | 연산 횟수 (N²) |
|---|---|---|
| 3×3 | 0.0008 | 9 |
| 5×5 | 0.0017 | 25 |
| 13×13 | 0.0071 | 169 |
| 25×25 | 0.0289 | 625 |

**O(N²)인 이유**
- `mac()`은 행 N개 × 열 N개를 모두 한 번씩 방문하며 곱셈과 덧셈을 1번씩 합니다.
- 따라서 연산 횟수는 정확히 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다.

**측정 결과와 연결**
- N이 5 → 25로 5배 커지면 연산 횟수는 25 → 625로 **25배** 늘어납니다.
- 실제 시간도 0.0017 → 0.0289 ms로 **약 17배** 늘어, N²에 비례해 커지는 경향을 보입니다.
- 25배보다 조금 적게 나오는 이유는 함수 호출 같은 **고정 비용**이 섞여 있기 때문입니다.
  크기가 작을수록 이 고정 비용의 비중이 커서 비율이 덜 깔끔하게 나옵니다.
- 시간 측정은 입력/출력/파일 읽기를 빼고 **MAC 함수 호출 구간만** 재서 연산 자체의 비용만 비교했습니다.

**NPU와의 연결**
- 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로 연산량이 N²로 폭발적으로 늘어납니다.
- CPU처럼 하나씩 순서대로 계산하면 감당하기 어렵기 때문에,
  수많은 MAC 연산을 **동시에(병렬로)** 처리하는 NPU가 필요합니다.
